行业痛点

每个项目，都是从零开始

01

项目碎片化

每个项目用不同仪器、不同流程，每次都要重新写一套软件，工程经验无法复用。

02

能力靠人不靠平台

测试逻辑散落在各个项目的代码里。人一走，下一个接手的工程师得花时间读懂前任的代码，才能继续推进。

03

质量难以标准化

开发者水平参差，同样需求写出截然不同的代码，维护成本和交付风险难以控制。

核心洞察

检测流程的底层逻辑不变
变的只是参数

Catalytic 把不变的逻辑固化为引擎，把变化的参数推到配置层，两者各守边界。

引擎层 — 不变的
✓连接仪器、发送指令、接收数据
✓按流程顺序执行测试步骤
✓判断结果是否合格（Pass / Fail）
✓处理超时、异常、重试逻辑
✓记录数据、生成测试报告
配置层 — 变化的
→使用哪台仪器、用什么协议
→发送什么指令、期望什么响应
→检查规则：范围 / 阈值 / 包含
→步骤执行顺序与跳转逻辑
→插件选择与参数配置

功能

从配置到运行，全程平台接管

01

低代码流程编排

通过图形界面添加测试步骤、定义设备指令与检查规则。换项目只需改配置，不动一行代码。支持 Pass / Fail / Timeout 各自独立跳转，覆盖非线性流程。

步骤管理跳转逻辑变量池
02

插件扩展系统

新仪器、新协议、MES 对接——开发一个插件即可，无需改动主框架。Communicator 负责通讯，Processor 处理业务逻辑，契约固定，实现自由。

TCP / UDP串口 / VISAMES 对接
03

多工位并行

每个工位（Slot）独立状态机、独立变量池、独立日志，各 Slot 并发调度，互不干扰，同步提升产线吞吐量。

独立状态机并发调度gRPC Stream

配置跨机迁移

配置文件导出为标准 JSON，包含设备类型、测试步骤和检查规则。导入即用，设备实例地址单独维护，不与配置耦合。

JSON 导出一键迁移批次切换

插件系统

非标逻辑，交给插件

Catalytic 的核心框架只做通用的事。凡是和具体业务有关的——用什么协议通讯、生成什么格式的报告、往哪个 MES 系统上报数据、跑什么自定义算法——全部通过插件实现，框架不感知，也不干涉。

Communicator 通讯插件

负责与仪器建立连接、收发数据。TCP、UDP、串口、VISA 各自一个插件，互不干扰。新仪器新协议，写一个插件就够，不动框架。

Processor 处理器插件

负责测试完成后的业务逻辑。报告生成、MES 数据上报、上位机遥控接入、自定义算法——这些需求千差万别，用插件实现，框架层面零修改。

插件契约

接口固定，实现自由

框架定义接口边界，插件只需实现约定，其余一概不管。

ICommunicator.cs 
// 框架定义通讯契约，插件负责具体实现
public interface ICommunicator
{
    // 协议标识，对应引擎回调的 protocol 参数
    string Protocol { get; }

    // 执行设备操作，返回响应数据
    Task<byte[]> ExecuteAsync(
        string address,
        byte[] payload,
        int    timeoutMs);
}

// 处理器契约：报告生成、MES 上报、自定义算法
public interface IProcessor
{
    string ProcessorId { get; }
    Task OnTestCompleteAsync(TestResult result);
}
